# Plugin Driver Rules

Tabularis ships a few built-in drivers, but any database can arrive as a plugin (`plugins/PLUGIN_GUIDE.md`), and built-in drivers are moving to plugins too. Every feature that touches a connection, a query or a table must say what happens with a plugin driver. "Works on PostgreSQL, MySQL and SQLite" is not enough.

1. **Decide and state plugin behaviour.** A PR that adds or changes a database feature says in its description whether plugin drivers get it, get a reduced version, or don't see it, and why. Silently showing a feature that will fail on a plugin is a bug.
2. **Branch on capabilities, not on driver ids.** Use the active `DriverCapabilities` (`activeCapabilities` from `DatabaseContext`) and helpers like `isPostgresDialect` / `isMysqlDialect`, which read `sql_dialect`. A check like `driver === "postgres"` misses plugins that speak the same dialect under another id (for example `postgresql`).
3. **Pass capabilities to SQL helpers.** Call `quoteIdentifier`, `quoteTableRef` and the filter/sort builders with `activeCapabilities ?? activeDriver`, so a plugin's `identifier_quote` and `sql_dialect` are honoured. A bare driver id falls back to `"` for anything that isn't MySQL/MariaDB.
4. **Generated SQL must fit the dialect or be gated.** SQL built in the frontend (`LIMIT`, `COUNT(DISTINCT …)`, `GROUP BY`, `ILIKE`, type casts, catalog queries) is only valid for some dialects. Either build it per `sql_dialect` (`postgres`, `mysql`, `mssql`, `sqlite`, `oracle`, `generic`) or hide the feature when the dialect can't run it. For something a plugin should compute natively, add an optional RPC with a capability flag, following `table_query_templates` / `get_table_query_template`.
5. **Hide, don't fail.** When a capability is missing (`views`, `routines`, `triggers`, `manage_tables`, `alter_column`, `explain`, `readonly`, …), the UI entry is hidden or disabled with a reason, not shown and left to error.
6. **Keep the plugin contract stable.** Slot contexts pass `driver` as the driver id string (`packages/web-ui/src/types/pluginSlots.ts`), because contributions are filtered with `ctx.driver === entry.driver`; never put a capabilities object there. Changing a slot context, a capability or an RPC means updating `packages/web-ui/src/types/plugins.ts`, `plugins/manifest.schema.json` and `plugins/PLUGIN_GUIDE.md` in the same PR.
7. **Test the plugin path.** Unit tests for driver-dependent logic include at least one case with a capabilities object (for example a custom `identifier_quote` or an unusual `sql_dialect`), not only the built-in driver ids.
